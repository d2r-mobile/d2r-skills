# 高保真设计参考图

把需求变成可看、可比较、可交给设计和开发继续工作的图。兼顾视觉完成度与交互可信度：用户应能看懂“加了什么、怎么用、不同状态是什么样”。中文请求默认中文沟通，图中文字服从产品语言。

## 先确定交付模式

| 用户意图 | 工作方式 | 默认交付 |
|---|---|---|
| 需求脑洞，尚无明确方向 | 从核心任务提出有实质差异的方向；没有指定数量时，先给两种，而不是多张换色图 | 可比较的概念图，各用一句话说明取舍 |
| 方向已定，需要设计参考 | 直接制作用户指定方案，不重新发起选型或要求先批准计划 | 完整场景中的高保真效果图，必要局部放大 |
| 修改截图或已有设计、二开 | 以现有界面为基准，圈定改动与保留项 | 改版效果图；有状态变化时提供同尺度状态对照 |

用户指定张数、样式、平台或只改一处时，优先遵守。不要自动把出图扩大成产品实现、发布网站或修改业务代码。

## 1. 读懂输入，再下笔

打开所有参考图片。能访问项目时，只读与目标界面相关的组件、样式和资源，确认真实结构。给每份输入指定角色：**修改底图、视觉风格参考、功能参考、禁止更动的依据**。多张图冲突时，优先采用用户明确指定的依据；只有会改变结果的冲突才提问。

从画面记录会影响设计的事实：画布比例、界面区域、视觉层级、边距与对齐、字号关系、色彩语义、材质、边框、图标风格、交互入口。区分图中可见事实、项目证据与设计假设。低清图看不清的小字不要猜成事实。

缺少关键编辑底图时，先检查已提供的路径；仍不可用再索取。新概念没有参考图也能推进，明确采用的视觉方向即可。只问影响布局、状态或改动边界的必要问题，不把创意任务变成长问卷。

这些参考图所代表的三种构图及适用情境见 [references/patterns.md](references/patterns.md)；需要选择展示形式时阅读。

## 2. 写一份短而具体的制作约束

在生成前整理下面的信息，不必逐项让用户确认：

- 用户任务：此画面帮助谁完成什么动作；本次设计要让用户判断什么。
- 改动范围：新增或调整哪些区域；哪些元素的位置、尺寸、内容和背景必须保留。
- 交互与状态：操作入口、反馈、关闭或返回；只列影响本次决策的状态。
- 文案与数据：需要逐字呈现的文本，真实数据来源或明确的示例数据。
- 画布与用途：完整界面、局部细节或对照板；以目标设备和参考图比例为准。
- 视觉标准：沿用哪些原有语言，重点提升哪些可见问题。

把“高级、专业”转换成可观察要求，例如：按钮边缘与面板边框一致、正文对比清楚、同级条目间距一致、操作区有稳定对齐线。不要靠堆砌发光、玻璃、渐变和装饰来冒充精致。

## 3. 选择可用的制作工具

- **生成或编辑位图效果图**：优先使用环境提供的图像生成/编辑工具；有 imagegen skill 时遵循其调用规范。先看编辑底图，再把底图与风格参考按角色传入。工具支持文件引用时使用真实路径；不要只把路径写进提示词当作已上传。
- **已有可编辑 UI、SVG 或 Figma 设计**：用户要求修改这些源文件时，在其原生格式中工作并导出效果图。只请求参考图时，不擅自修改生产文件；使用独立草稿或副本。
- **明确要求可运行原型或精确排版的代码画布**：用 HTML/CSS/SVG 等制作，并实际渲染、截图验证。可编辑源文件和图片各自交付。
- 不用一份文字提示词冒充已完成的参考图。图像工具不可用时，说明限制，可先交付制作 brief；不要假称生成成功，也不要未经用户同意切换到需要密钥或付费的外部服务。

具体提示词结构、两类任务的示例及验收门槛见 [references/production.md](references/production.md)。制作与复核时阅读。

## 4. 做到像真实产品，而不是示意拼贴

继承参考的视觉语言，而不是照抄其模糊、错字或粗糙排版。暗黑游戏可以保留石材、旧金属、克制的金色和暗底；其他产品沿用自己的设计系统。

- 先处理信息结构和可读性，再细化材质、边缘、光影和图标。控制纹理强度，使其不压过内容。
- 一套字体层级、一套间距节奏、统一图标尺度与透视。新增控件应像原生组件，避免贴纸感。
- 标题、正文、数量、状态、主操作有清楚层级。颜色不是唯一状态线索，辅以文字、数值或符号。
- 多状态对照使用同一底图、裁切、缩放、控件坐标和光照，避免用户把无关漂移当成功能变化。
- 保留的区域要逐项比对。生成式编辑可能改变未指定区域，不能承诺像素级不变；发现漂移就修正。若用户要求严格像素一致，明确需要可编辑源文件或精确合成能力；不要把近似结果标为精确完成。
- 手机或平板场景要按实际显示大小检查；角标不能挡住图标，数量不能超出按钮，文字不能侵占操作区域。没有尺寸或实现证据时，不声称触控尺寸已经达标。

## 5. 用状态说明设计，而不是只画漂亮的静态图

依需求选择必要状态，不机械地为每次任务画全套状态。

- 可执行与不可执行：按钮是否可用，缺少的条件是什么，下一步是什么。
- 计数与耗尽：有余量、为零时的显示与动作；不要擅自把“不可用”改成“隐藏”。
- 收藏或列表：已有、缺失、历史收录、完整收集之间如何区分；可点击区域与反馈是什么。
- 弹窗：触发入口、主动作、关闭规则，必要时说明加载或失败反馈。

新想法可以提出新机制，但标为建议。二开任务里未获指定的行为不要悄悄改变。游戏规则、物品名称和数值以用户或项目为依据，无法确认时用明确标注的示例数据。

## 6. 看图验收，再交付

必须打开实际输出，按 [制作与验收标准](references/production.md#验收门槛) 检查完整图和关键局部。先修复错字、错误状态、布局漂移等硬问题，再微调审美。针对失败点做局部迭代，不每轮推翻整张图。

默认最多进行两轮针对性修正；仍有关键缺陷时明确指出未通过项，并提出需要的素材或工具。两轮生成修正也不能保证严格像素保留；未达到保持要求时不得降级标准后宣布完成。不要将不合格稿称为最终稿，不以自评分数代替检查。

按任务规模交付：

1. **干净效果图**：供直接评审，文字清楚、画面完整。用户只要单图时不额外制作整套报告。
2. **状态或改动标注图**：确有必要时单独提供；编号与短注放在独立边栏，不覆盖操作区，不把标注做成产品控件。
3. **简短二开说明**：修改区域、保留项、关键状态与操作规则、待确认假设。用户要求实现交接时补充布局关系、颜色/字号建议及资源需求；测量值与建议值分开。

保存到用户指定位置；项目交付放进项目目录，默认使用版本化名称，保留原图。为需后续迭代的项目附上简短制作 brief、最终提示词和输入角色映射，不记录无关本机路径或凭据。只提交本次授权发布的材料；参考图供分析不等于授权把它们上传公共仓库。

最终回复展示或链接实际图片，概括方案与未解决项。明确高保真参考图与已经实现、测试的产品界面的区别。
